# Практикум 6: Модульний дизайн, або Як не писати "крихкий" код (DIP, IoC, DI)

> **Декларація курсу.** Академічна доброчесність та авторство матеріалів — у [DISCLAIMER.md](DISCLAIMER.md).


## Експрес-опитування: Згадуємо SOLID

На [попередньому практикумі](p05_solid.md) ми розглядали рефакторинг монолітного коду. Пригадаємо ключові моменти:

1. **"D" (DIP):** Як формулюється Принцип інверсії залежностей?
2. **Проблема DIP на практиці:** Яку проблему ми спостерігаємо в класі `OrderProcessor`, якщо він всередині себе жорстко викликає `new MySQLOrderRepository()`?
3. **"S" (SRP):** Чому клас, який одночасно читає конфігурацію з файлу *і* відправляє мережеві повідомлення, вважається поганим архітектурним рішенням?

<details markdown="1">
<summary>Очікувані відповіді</summary>

1. **DIP (Dependency Inversion Principle):** Модулі вищого рівня не повинні залежати від модулів нижчого рівня. Обидва типи модулів мають залежати від **абстракцій** (інтерфейсів).
2. **Проблема:** `OrderProcessor` (бізнес-логіка вищого рівня) виявляється жорстко прив'язаним до конкретної бази даних `MySQLOrderRepository` (деталь інфраструктури). Заміна СУБД на PostgreSQL або зберігання у хмарі змусить нас **модифікувати** сам `OrderProcessor`, що порушує OCP і ускладнює написання юніт-тестів без реальної БД.
3. **SRP (Single Responsibility Principle):** Такий клас має щонайменше **дві незалежні причини для змін**: зміна формату або джерела конфігурації (файл, БД, змінні середовища) та зміна протоколу або логіки доставки повідомлень.

</details>

Цей практикум присвячений трьом ключовим концепціям створення гнучких систем: **DIP**, **IoC** (Inversion of Control) та техніці їх реалізації — **Dependency Injection (DI)**.

## Вступ

Поширена інженерна думка стверджує, що «ідеального коду, який можна перевикористати скрізь, не існує». Проте успішні open-source бібліотеки та корпоративні фреймворки доводять: якщо архітектура побудована навколо слабкої зв'язності (loose coupling), код стає гнучким і довговічним.

Сьогодні ми простежимо шлях від примітивної, але крихкої реалізації до модульного дизайну на прикладі **бота для Discord**, що розсилає системні сповіщення.

Зверніть увагу: принципи модульності, розглянуті тут, є базою для вашого фінального проєкту (модульної гри), де логіка також розвиватиметься через розширення вимог.

## Еволюція дизайну: від хардкоду до гнучкого сервісу

### Версія 1: «Працює — і добре»

Початкове завдання: надіслати тестове повідомлення в конкретний канал Discord. 

Реалізація «в лоб»:

```java
public class NotificationBot {
    public void sendMessage() {
        String apiToken = "hardcoded-token-from-discord";
        long channelId = 123456789012345678L;
        String message = "Привіт!";

        // Логіка підключення до Discord API та відправки...
        System.out.printf("Надсилаю '%s' в канал %d, використовуючи токен...%n", message, channelId);
    }
}
```

**Архітектурні та безпекові недоліки:**
1. **Жорсткий зв'язок (Tight Coupling):** Зміна тексту, каналу або токена вимагає редагування вихідного коду та перекомпільовування програми.
2. **Критична проблема безпеки:** Зберігати секретні токени у вихідному коді — неприпустимо. Автоматичні боти на GitHub та Bitbucket сканують публічні коміти в режимі реального часу і перехоплюють злиті токени за лічені секунди після пушу.

---

### Версія 2: Додавання параметрів

**Нова вимога бізнесу:** бот має надсилати довільні повідомлення у різні канали.

```java
public class NotificationBot {
    private final String apiToken = "hardcoded-token-from-discord"; // Токен все ще захардкоджений

    public void sendMessage(long channelId, String message) {
        // Логіка підключення та відправки...
        System.out.printf("Надсилаю '%s' в канал %d...%n", message, channelId);
    }
}
```

**Чи вирішено проблему?** Лише частково. Канал та повідомлення параметризовані, але джерело авторизації (токен) залишається незмінним і «зашитим» усередині класу.

---

### Нова вимога, яка ламає початковий підхід

**Реальний сценарій:**
1. Бот має працювати на двох різних оточеннях: `staging` (тестовий сервер з тестовим токеном) та `production` (робочий сервер).
2. Налаштування мають завантажуватися не зі статичних значень: для локального запуску — з файлу конфігурації, а на сервері — з бази даних або змінних середовища.

Якщо клас `NotificationBot` сам намагатиметься відкривати файл або йти до бази даних, він порушить SRP, стане залежним від конкретних бібліотек читання файлів чи драйверів БД і перетвориться на крихкий моноліт.

## Застосування принципів дизайну

Щоб зробити сервіс стійким до змін, розділимо його на контракти та реалізації.

### 1. Принцип інверсії залежностей (DIP)

> Модулі вищого рівня не повинні залежати від модулів нижчого рівня. Обидва мають залежати від абстракцій.

`NotificationBot` — це модуль вищого рівня (бізнес-сервіс сповіщень). Його завдання — сформувати та надіслати повідомлення. 
Він взагалі не повинен знати, *звідки* взялися параметри підключення: з файлу `config.properties`, з таблиці PostgreSQL чи з хмарного сервісу параметрів. 

Він повинен залежати лише від **контракту** (інтерфейсу):

```java
public interface BotConfig {
    String getToken();
    long getDefaultChannelId();
}
```

---

### 2. Принцип єдиного обов'язку (SRP)

> Клас повинен мати лише один обов'язок.

Відокремлюємо обов'язок **читання конфігурації** від обов'язку **відправки повідомлень**:
* `NotificationBot` відповідає виключно за відправку повідомлень.
* За роботу з джерелами конфігурації відповідають окремі класи, що реалізують спільний інтерфейс:

```java
// Відповідає тільки за парсинг та читання файлу
public class FileBotConfig implements BotConfig {
    // ... логіка читання з файлу ...
}

// Відповідає тільки за вичитку конфігурації з БД
public class DatabaseBotConfig implements BotConfig {
    // ... логіка читання з бази даних ...
}
```

---

### 3. Інверсія контролю (IoC) та Впровадження залежностей (DI)

Часто виникає плутанина між цими термінами. Розглянемо їх чітке розмежування:

* **Inversion of Control (IoC) — це архітектурний принцип:** 
  Контроль над життєвим циклом та створенням залежностей передається від внутрішнього коду компонента до зовнішнього середовища.
* **Dependency Injection (DI) — це конкретний патерн реалізації IoC:** 
  Замість того, щоб об'єкт самостійно створював свої залежності через оператор `new`, вони передаються («впроваджуються») йому ззовні (найчастіше через параметри конструктора).

> **Аналогія з життя:**
> * **Без DI:** Ви виходите на нову роботу в перший день. Вам видають записку і кажуть: «Йди на склад, сам знайди стіл, вибери стілець, притягни системний блок і підключи дроти». Ви витрачаєте сили на пошук і збирання робочого місця замість виконання своїх прямих обов'язків.
> * **З DI:** У перший робочий день ви заявляєте свої потреби: «Для виконання моєї роботи мені потрібні стіл, стілець та комп'ютер». Ви приходите на робоче місце, де все це вже встановлено і підключено. Ви просто виконуєте свою роботу, не турбуючись про те, звідки ці предмети взялися.

## Фінальна архітектура: Модульний бот

### 1. Абстракція (Контракт)

```java
// BotConfig.java
public interface BotConfig {
    String getToken();
    long getDefaultChannelId();
}
```

### 2. Реалізації контрактів конфігурації

```java
// FileBotConfig.java
public class FileBotConfig implements BotConfig {
    private final String token;
    private final long channelId;

    public FileBotConfig(String configFilePath) {
        // Читання налаштувань із файлу properties/json
        this.token = "...";
        this.channelId = 123456789L;
    }

    @Override
    public String getToken() {
        return token;
    }

    @Override
    public long getDefaultChannelId() {
        return channelId;
    }
}
```

### 3. Модуль вищого рівня з впровадженням залежності (Constructor Injection)

```java
// NotificationBot.java
public class NotificationBot {
    private final BotConfig config;

    // Залежність декларується як контракт і надається ззовні
    public NotificationBot(BotConfig config) {
        this.config = config;
    }

    public void sendDefaultMessage(String message) {
        String token = config.getToken();
        long channelId = config.getDefaultChannelId();
        System.out.printf("Надсилаю '%s' в канал %d...%n", message, channelId);
    }
}
```

### 4. Точка збирання (Assembler / Main)

```java
// Main.java
public class Main {
    public static void main(String[] args) {
        // Рішення про те, яке саме джерело налаштувань використати, приймається ззовні
        BotConfig config = new FileBotConfig("bot.properties");
        // За потреби замінюється на: new DatabaseBotConfig("jdbc:...")

        // Збираємо систему: передаємо залежність у бота
        NotificationBot bot = new NotificationBot(config);

        bot.sendDefaultMessage("Принципи дизайну роблять код гнучким!");
    }
}
```

**Результат:**
* `NotificationBot` повністю відв'язаний від формату зберігання налаштувань.
* Його легко покрити юніт-тестами, передавши тестовий mock/stub реалізації `BotConfig`.
* Додавання нових джерел конфігурації (змінні оточення, AWS SSM, HashiCorp Vault) не вимагає модифікації жодного рядка в класі `NotificationBot`.

## Контрольні питання

1. **DIP.** Що означає вимога «залежати від абстракцій, а не від конкретних реалізацій» на прикладі нашого бота?
2. **SRP.** Який обов'язок має клас `FileBotConfig` у модульній версії програми?
3. **IoC vs DI.** У чому полягає різниця між Інверсією Контролю (IoC) та Впровадженням Залежностей (DI)? Хто відповідає за зв'язування компонентів у нашому коді?
4. **OCP.** Якщо потрібно брати конфігурацію зі змінних середовища (Environment Variables), які кроки необхідно виконати? Чи зміниться при цьому код `NotificationBot`?

<details markdown="1">
<summary>Очікувані відповіді</summary>

1. **DIP:** `NotificationBot` (високий рівень) знає лише про інтерфейс `BotConfig` (контракт) і не має прямих зв'язків з `FileBotConfig` або `DatabaseBotConfig`. Йому байдуже джерело походження даних, доки об'єкт надає коректний токен та ID каналу.
2. **SRP:** Єдиний обов'язок `FileBotConfig` — вичитування та валідація налаштувань із файлової системи. Клас не знає, як саме ці дані будуть використані для надсилання повідомлень у мережу.
3. **IoC vs DI:**
   * **IoC:** загальний принцип передачі контролю над залежностями зовнішньому середовищу.
   * **DI:** конкретна техніка передачі залежностей у клас (у нашому випадку — через конструктор).
   * **Відповідальний за зв'язування:** клас `Main` (компонувальник/Assembler), а у промислових додатках — DI-контейнер фреймворку (наприклад, Spring Core).
4. **OCP:**
   1. Створюється новий клас `public class EnvBotConfig implements BotConfig`.
   2. У ньому реалізуються методи читання з `System.getenv(...)`.
   3. У точці складання (`Main`) створюється екземпляр `new EnvBotConfig()`.
   * **Клас `NotificationBot` залишається незмінним**, система розширюється без модифікації існуючого сервісу.

</details>
