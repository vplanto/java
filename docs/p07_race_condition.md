## ⚡ Експрес-опитування: Згадуємо основи

На [Лекції 6](06_threads.md) ми розглянули теорію паралельних обчислень. Давайте швидко перевіримо себе перед кодом:

1.  У чому полягає **"стан гонитви" (race condition)**?
2.  Яка принципова різниця між `thread.start()` та `thread.run()`?
3.  Що робить метод `thread.join()`?

<details markdown="1">
<summary>Наші очікування (відповідь)</summary>

1.  **Race Condition (Стан гонитви):** Ситуація, коли два або більше потоків одночасно намагаються **змінити** спільні дані без належної синхронізації. Результат виконання стає недетермінованим і залежить від випадкового порядку, в якому операційна система перемикає потоки на ядрах CPU.
2.  **`start()` vs `run()`:** Виклик `start()` надсилає запит JVM та операційній системі виділити **новий потік виконання** (зі своїм окремим стеком викликів) і вже в ньому виконати метод `run()`. Прямий виклик `run()` — це звичайний синхронний виклик методу в **поточному** потоці, без створення нового потоку і без будь-якого паралелізму.
3.  **`join()`:** Змушує потік, що його викликав (наприклад, `main`), **заблокуватися і чекати**, доки цільовий worker-потік повністю не завершить своє виконання і не перейде у стан `TERMINATED`.

</details>

Сьогодні ми побачимо **race condition** в дії та навчимося його надійно "лікувати" на реалістичному сценарії.

## Вступ

На [Практикумі 4](p04_collections.md) ми вже моделювали предметну область Monobank у контексті колекцій. Сьогодні ми зазирнемо у бекенд однієї з найвідоміших та найвідповідальніших функцій в Україні — **«Банки» для збору донатів**.

Уявіть масштабний благодійний збір: тисячі людей одночасно відкривають посилання та натискають кнопку «Задонатити 10 грн». Усі ці запити летять на бекенд-сервер, де в пам’яті існує єдиний лічильник зібраної суми.

**Критерій успіху нашого практикуму:** створити симулятор збору коштів, переконатися на власні очі у втраті грошей через стан гонитви, а потім виправити код так, щоб жодна гривня не зникала, навіть якщо тисячі донаторів відправляють кошти в одну й ту саму мілісекунду.

> Повна теорія організації потоків у Java, апаратних кешів CPU та інших інструментів конкурентності викладена в [Лекції 6: Подорож у світ паралельних обчислень](06_threads.md). Тут ми фокусуємося на наскрізній практичній історії «Банки».

## Теоретичний мінімум перед стартом коду

Для нашого експерименту нам потрібні три ключові концепції:

1.  **Спільний ресурс (Shared State):** Один екземпляр класу `DonationJar`, що зберігає баланс збору.
2.  **Паралельні виконавці (`Thread` + `Runnable`):** Багато потоків, кожен з яких виконує дію «внести донат» за допомогою лямбда-виразу. Запуск — виключно через метод `start()`.
3.  **Координація (`join()`):** Головний потік програми (`main`) повинен обов'язково дочекатися завершення всіх транзакцій, перш ніж підбивати підсумки та виводити фінальний баланс.

## Проблема: «Втрачені донати»

Уявімо, що ми — команда розробників, і нам поставили завдання реалізувати базову логіку збереження балансу «Банки». Почнемо з наївної, небезпечної реалізації.

```java
// DonationJar.java (Версія 1: Небезпечна)
public class DonationJar {
    private long totalDonations = 0;

    // Метод викликається щоразу, коли надходить новий донат
    public void donate(long amount) {
        // УВАГА: Ця операція НЕ є атомарною!
        // 1. Прочитати поточне значення totalDonations з пам'яті
        // 2. Додати до нього amount
        // 3. Записати обчислене значення назад у totalDonations
        totalDonations += amount;
    }

    public long getTotalDonations() {
        return totalDonations;
    }
}
```

Тепер проведемо стрес-тест: змоделюємо ситуацію, коли **2000 людей** одночасно роблять внесок по **10 грн**. Математично ми очікуємо рівно **20 000 грн** ($2000 \times 10$).

```java
// Main.java (Симулятор одночасного збору)
public class Main {
    public static void main(String[] args) throws InterruptedException {
        DonationJar jar = new DonationJar();
        int numberOfDonators = 2000;
        long donationAmount = 10;

        // Задача для кожного потоку-донатора
        Runnable donationTask = () -> jar.donate(donationAmount);

        // Створюємо 2000 "людей", які одночасно відправляють гроші
        Thread[] donators = new Thread[numberOfDonators];
        for (int i = 0; i < numberOfDonators; i++) {
            donators[i] = new Thread(donationTask);
        }

        // Запускаємо всі потоки — донати пішли паралельно!
        for (Thread donator : donators) {
            donator.start();
        }

        // Чекаємо, доки ВСІ донатори завершать свої операції
        for (Thread donator : donators) {
            donator.join();
        }

        System.out.println("Очікувалось зібрати: " + (numberOfDonators * donationAmount) + " грн");
        System.out.println("Фактично зібрано:   " + jar.getTotalDonations() + " грн");
    }
}
```

### Результати запуску симулятора

Якщо запустити цей код кілька разів поспіль, фактично зібрана сума майже завжди виявляється меншою за 20 000 грн (наприклад, 18 450 грн або 19 120 грн). Частина операцій безповоротно втрачається.

Це класичний прояв **стану гонитви (race condition)**: коли кілька потоків одночасно змінюють спільний стан без належної синхронізації, результат стає некоректним і залежить від випадкового порядку виконання інструкцій.

### Чому результат змінюється при кожному запуску (недетермінізм)

Зверніть увагу: підсумкове значення різне під час кожного запуску. На комп'ютері з низьким навантаженням розбіжність може бути мінімальною, тоді як на навантаженому сервері — суттєвою.

Успішне проходження тесту при разовому запуску **не доводить** коректності багатопотокового коду. Планувальник операційної системи розподіляє кванти часу між потоками недетерміновано, тому дефекти такого типу складно виявити під час локальної розробки: зазвичай вони проявляються вже у продакшені під високим навантаженням.

### Механізм втрати даних: покроковий розбір

Оператор `totalDonations += amount` у байткоді Java складається з трьох послідовних кроків:
1. **Read:** прочитати поточне значення з пам’яті (або кешу CPU) у регістр процесора.
2. **Modify:** додати `amount` до значення в регістрі.
3. **Write:** записати оновлений результат назад у спільну пам’ять.

Якщо два потоки (Потік А і Потік Б) виконують метод одночасно, їхні операції перетинаються в часі:

| Час ($t$) | Потік А (перший донатор) | Потік Б (другий донатор) | Баланс у спільній пам'яті |
|:---:|---|---|:---:|
| $t_1$ | Читає `totalDonations` (значення **1000**) | *ще очікує запуску* | 1000 |
| $t_2$ | Обчислює $1000 + 10 = 1010$ | Читає `totalDonations` (теж бачить **1000**) | 1000 |
| $t_3$ | Записує **1010** у пам'ять | Обчислює $1000 + 10 = 1010$ | 1010 |
| $t_4$ | *завершив виконання* | Записує **1010** у пам'ять (перезаписує результат А) | **1010** |

**Підсумок:** Хоча надійшло два окремі платежі по 10 грн, баланс збільшився лише на 10 грн замість 20 грн. Запис другого потоку перекрив результат першого — це класична проблема **втраченого оновлення (Lost Update)**.

## Рішення: `synchronized` — гарантія кожної гривні

Щоб унеможливити таку проблему, нам необхідно зробити блок «прочитати → додати → записати» **неподільним (атомарним)**. Іншими словами, поки один потік оновлює баланс банки, жоден інший потік не має права втручатися в цей процес.

У Java для цього існує ключове слово **`synchronized`**. Воно використовує вбудований у кожен Java-об'єкт **монітор (м'ютекс / замок)**:

* Коли потік викликає `synchronized`-метод, він автоматично **захоплює замок** цього екземпляра (`this`).
* Якщо інший потік намагається викликати цей же синхронізований метод, він не може цього зробити: JVM переводить його у стан **`BLOCKED`** і ставить у чергу очікування біля дверей «кабінки».
* Коли перший потік завершує метод, він автоматично **відпускає замок**, і наступний потік із черги отримує доступ.

Давайте модифікуємо наш клас:

```java
// DonationJar.java (Версія 2: Потокобезпечна)
public class DonationJar {
    private long totalDonations = 0;

    // Ключове слово synchronized гарантує взаємне виключення (Mutual Exclusion)
    public synchronized void donate(long amount) {
        totalDonations += amount;
    }

    public synchronized long getTotalDonations() {
        return totalDonations;
    }
}
```

> [!NOTE]
> **Для допитливих інженерів:** Зверніть увагу, що ми додали `synchronized` не лише на `donate()`, а й на гетер `getTotalDonations()`. Чому? У багатопотокових системах важливо гарантувати не лише атомарність запису, а й **видимість (visibility)** актуального значення для читача. Якщо читати поле без синхронізації (або без `volatile`), читаючий потік може взяти застаріле значення з кешу свого ядра CPU.

Тепер знову запустіть `Main.java` — результат **завжди буде стабільно рівним 20 000 грн**. Жодна гривня більше не губиться.

### Порівняння продуктивності: Скільки коштує `synchronized`?

У конкурентному програмуванні потокобезпечність має ціну в продуктивності. Щоб наочно виміряти накладні витрати синхронізації, у модулі `thread-samples` підготовлено бенчмарк `org.example.DonationJarSample` (файл `DonationJarSample.java`).

Замір часу виконання здійснюється за допомогою `System.currentTimeMillis()` або `System.nanoTime()`:

```java
long startTime = System.currentTimeMillis();
for (Thread t : threads) t.start();
for (Thread t : threads) t.join();
long durationMs = System.currentTimeMillis() - startTime;
```

| Варіант реалізації | Фактичний баланс | Втрачено коштів | Час виконання | Статус результату |

## Координація потоків: Навіщо потрібен `join()`?

У симуляторі ми використали цикл очікування:

```java
for (Thread donator : donators) {
    donator.join();
}
```

Метод `join()` змушує потік, що його викликав (у нашому випадку потік `main`), **зачекати**, поки цільовий потік завершить роботу і перейде у стан `TERMINATED`.

У термінах станів потоків (детально розібраних у [Лекції 6](06_threads.md)), `main` переходить у стан **`WAITING`**.

> **Експеримент:** Спробуйте закоментувати цикл з `donator.join()` у `Main.java` і запустити програму.
> Ви майже напевно побачите:
> ```text
> Очікувалось зібрати: 20000 грн
> Фактично зібрано:   0 грн
> ```
> Чому? Потік `main` миттєво створив потоки, сказав їм `start()` і, не чекаючи виконання повільних операцій в операційній системі, одразу побіг далі та надрукував баланс. Це все одно, що підбивати фінансові підсумки благодійного збору, коли люди ще навіть не встигли дістати гаманці!

## Після Банки: Куди рухаємось далі?

Сьогодні ви на реальному прикладі побачили силу та простоту ключового слова `synchronized`. Проте в інженерії кожне рішення має свою ціну:

* **Ціна `synchronized` — блокування:** Поки один потік знаходиться всередині методу `donate()`, усі інші 1999 потоків **стоять у черзі** і нічого не роблять. Для простого додавання це не відчувається, але для складних методів синхронізація може стати вузьким місцем (bottleneck).
* **Створення тисяч потоків вручну — це антипатерн:** Створити 2000 об'єктів `new Thread()` у нашому симуляторі — це штучний стрес-тест. У реальному серверному додатку створення окремого системного потоку на кожен HTTP-запит швидко призведе до вичерпання пам'яті (пам'ять під стек) та помилки `OutOfMemoryError: unable to create native thread`. Як правильно організовувати роботу з обмеженою кількістю потоків за допомогою пулів — розбираємо на [Практикумі 9: Не створюйте потоки вручну! Сила ExecutorService](p09_executors.md).
* **Альтернативи без блокування (Lock-Free):** Якщо все, що нам потрібно, — це потокобезпечний лічильник грошей, набагато ефективнішим рішенням є класи з пакету `java.util.concurrent.atomic` (наприклад, `AtomicLong`), які ми вивчаємо у [Лекції 6](06_threads.md). Вони використовують апаратні інструкції CPU (CAS — Compare-And-Swap) і оновлюють значення взагалі без блокування потоків!
* **Віртуальні потоки (Java 21+):** Для систем, які обробляють мільйони запитів одночасно, сучасна Java пропонує віртуальні потоки (Project Loom), які не займають дорогі ресурси операційної системи (детальніше — у [Лекції 6](06_threads.md)).

## Контрольні питання

1.  **Проблема.** Поясніть своїми словами послідовність дій двох потоків, через яку виникає втрата 10 грн при операції `totalDonations += amount`.
2.  **Теорія.** Чому прямий виклик `donator.run()` не створить багатопотоковості, а виклик `donator.start()` створить?
3.  **Рішення.** Які гарантії надає ключове слово `synchronized`? Чому версія 2 `DonationJar` гарантує збереження всіх донатів?
4.  **Координація.** Що станеться, якщо прибрати виклики `join()` із симулятора? У якому стані перебуває потік `main`, поки чекає донаторів?
5.  **Аналогія.** Уявіть, що двоє людей одночасно редагують спільний документ (наприклад, у Google Docs або репозиторії Git). Які проблеми, аналогічні до "стану гонитви", можуть виникнути, якщо система не забезпечить синхронізацію?

<details markdown="1">
<summary>Еталонні відповіді (перевірте себе)</summary>

1.  **Послідовність втрати донату:**
    Операція `totalDonations += amount` складається з трьох неподільних кроків: 1) читання значення з пам'яті, 2) додавання суми в регістрі, 3) запис нового значення назад. Якщо Потік А читає 1000 і обчислює 1010, але до його запису в пам'ять втручається Потік Б і теж встигає прочитати старе значення 1000, обидва потоки обчислять однаковий результат 1010 і запишуть його в пам'ять один за одним. Замість приросту на 20 грн баланс збільшиться лише на 10 грн — один донат безповоротно втрачено (проблема **Lost Update**).
2.  **`start()` vs `run()`:**
    Метод `start()` звертається до JVM та операційної системи з вимогою виділити новий стек пам'яті та зареєструвати новий потік в системному планувальнику задач, після чого в ньому асинхронно стартує `run()`. Якщо викликати `run()` напряму, це звичайнісінький виклик методу класу: код виконається послідовно в поточному потоці `main`, нового системного потоку не виникне, і всі 2000 донатів пройдуть строго один за одним без жодної паралельності.
3.  **Гарантія `synchronized`:**
    Ключове слово `synchronized` гарантує **взаємне виключення (mutual exclusion)**. Метод може одночасно виконувати лише один-єдиний потік для даного екземпляра об'єкта. Усі інші потоки блокуються (переходять у стан `BLOCKED`) і чекають у черзі біля монітора. Таким чином, складена операція "читання-модифікація-запис" стає атомарною для сторонніх спостерігачів.
4.  **Без `join()`:**
    Потік `main` відправить команди `start()` усім 2000 потокам і, не чекаючи навіть початку їхньої реальної роботи, миттєво перейде до наступного рядка коду — виведення балансу. Результатом майже напевно буде "Фактично зібрано: 0 грн" або випадкова мала проміжна сума. Під час виклику `join()` потік `main` переходить у стан `WAITING` до моменту, поки цільовий потік не перейде у стан `TERMINATED`.
5.  **Аналогія з документами (Google Docs / Git):**
    * **Втрачене оновлення (Lost Update):** Користувач А завантажив файл версії 1 і почав редагувати абзац. Користувач Б завантажив той самий файл версії 1, змінив інше речення і зберіг версію 2. Якщо користувач А просто збереже свою версію поверх, він затре правки користувача Б, бо його редагування базувалося на застарілому стані.
    * **Конфлікт редагування (Merge Conflict):** Одночасна несумісна зміна одного й того самого рядка двома авторами, що вимагає втручання механізму синхронізації або ручного вирішення.

</details>
