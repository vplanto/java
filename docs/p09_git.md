# Практикум 9: Командна робота з Git та розв'язання конфліктів

> **Декларація курсу.** Академічна доброчесність та авторство матеріалів — у [DISCLAIMER.md](DISCLAIMER.md).


## Експрес-опитування: Згадуємо основи

На [Практикумі 0](p00_git_github.md) ми налаштували Git для здачі домашніх завдань. Давайте пригадаємо:

1.  Яка різниця між `git commit` та `git push`?
2.  Навіщо ми створювали файл `.gitignore`?
3.  Що робить команда `git clone`?

<details markdown="1">
<summary>Наші очікування (відповідь)</summary>

1.  **`git commit`** зберігає "знімок" (версію) ваших файлів у **локальному** репозиторії (на вашому комп'ютері). **`git push`** відправляє ваші локальні коміти у **віддалений** репозиторій (на GitHub).
2.  `.gitignore` вказує Git, які файли (напр., `.class` або `target/`) *не* потрібно відстежувати і додавати до репозиторію.
3.  `git clone` робить локальну копію віддаленого репозиторію з GitHub на ваш комп'ютер.

</details>

Сьогодні ми переходимо від індивідуальної роботи до **командної**.

## Вступ

Сьогодні ми розберемо основний інструмент командної розробки — Git.

Уявіть, що ви з колегами **одночасно працюєте над одним спільним проєктом** (наприклад, веб-сервісом для логістичної організації). Як організувати процес так, щоб зміни одного розробника не перезаписали роботу іншого?

Наша мета сьогодні — розібрати механіку синхронізації змін у Git і пройти шлях від клонування спільного репозиторію до розв'язання конфлікту злиття (merge conflict) та роботи з гілками.

**Наш кінцевий продукт:** Чіткий і безпечний **робочий процес (workflow)** для командної розробки.

-----

## Теоретичний мінімум: Локальний та віддалений репозиторії

Щоб не плутатись, запам'ятайте базову модель:

  * **Git-репозиторій — це журнал станів вашого проєкту.**
  * **`commit` (коміт)** — це зафіксований знімок (snapshot) коду в певний момент часу.

Git оперує двома копіями цього журналу:

1.  **Локальний репозиторій (Local):** Ваша робоча копія, яка лежить на комп'ютері у прихованій папці `.git`. Усі коміти та перемикання гілок спочатку відбуваються локально.
2.  **Віддалений репозиторій (Remote):** Спільний репозиторій на сервері (GitHub, GitLab), через який команда обмінюється змінами.

Весь процес командної роботи з Git — це синхронізація локального репозиторію з віддаленим.

-----

## Крок 1: Початок роботи (Клонування)

Щоб почати працювати над проєктом, вам потрібно отримати копію спільного репозиторію з GitHub.

**Послідовність дій до клонування:**

1.  Хтось (Team Lead або ви) має *створити* цей спільний репозиторій на GitHub.
2.  Ви отримуєте посилання (URL) на нього, наприклад: `https://github.com/volunteer-org/website.git`.

**Що означає "клонувати"?**
Команда `git clone [URL]` завантажує повну історію спільного репозиторію з GitHub і створює локальний репозиторій (папку `.git`) на вашому комп'ютері.

```bash
# Виконується в терміналі
git clone https://github.com/volunteer-org/website.git
```

#### Типова помилка: "Клон всередині клону"

**Що не можна робити:** Заходити в папку, яка *вже є* Git-репозиторієм (наприклад, в `website`), і виконувати `git clone` ще раз всередині неї.

  * **Чому?** Ви створюєте вкладений репозиторій (папка `.git` всередині іншої папки `.git`). Це призводить до конфлікту шляхів, і Git не відстежуватиме вкладену директорію як звичайні файли батьківського проєкту.
  * **Правило:** Один проєкт = одна папка = один `git clone`.

## Крок 2: Щоденний робочий цикл (4 кроки)

Коли ви постійно працюєте над проєктом, робочий цикл складається з чотирьох кроків:

1.  **`git pull` (Оновитися)**

      * **Що робить:** Завантажує нові коміти з віддаленого репозиторію (GitHub) у ваш локальний.
      * **Навіщо:** Щоб починати роботу з актуальної версії коду, яку вже оновили колеги.
      * **Правило:** *Завжди* виконуйте `pull` перед початком нової задачі.

2.  **`git add .` (Підготувати до коміту)**

      * **Що робить:** Переносить змінені файли до індексу (staging area) для наступного коміту.

3.  **`git commit -m "Опис змін"` (Зафіксувати знімок)**

      * **Що робить:** Створює коміт із підготовлених файлів і **зберігає його у локальному репозиторії**.
      * **Важливо:** Повідомлення коміту має стисло описувати суть змін (не "fix", а "Виправив помилку валідації у логіні").

4.  **`git push` (Відправити зміни в спільний репозиторій)**

      * **Що робить:** Завантажує ваші нові локальні коміти на сервер (GitHub). Тільки після цього команда побачить вашу роботу.

**Послідовність:** `pull` -> (працюємо) -> `add` -> `commit` -> `push`.

## Крок 3: Розходження історії (`! [rejected]`)

Розглянемо типовий сценарій одночасної роботи двох розробників:

  * **Ви (Розробник 1):** Зранку зробили `git pull`. Починаєте працювати над `index.html`, додаючи розділ "Контакти".
  * **Ваш колега (Розробник 2):** В цей час теж працює. Він додає в `index.html` розділ "Звіти" і робить `push`.

Тепер **віддалений репозиторій (`remote`) має новіші коміти**, яких ще немає у вас.

Ви закінчуєте свою роботу, робите `git add .` та `git commit -m "Додав контакти"`. Тепер *ваш локальний репозиторій* теж має власний коміт.

Ви намагаєтесь виконати `git push` і отримуєте відмову: `! [rejected]`

**Що сталося?** На сервері вже є коміт вашого колеги, якого немає у вашій локальній історії. Git блокує прямий запис, щоб не перезаписати чужі зміни і не втратити розділ "Звіти".

-----

## Крок 4: Як оновити локальну версію (Рішення)

Ваше завдання — **об'єднати** зміни колеги та ваші зміни. Є два шляхи.

### Шлях 1: Простий (але "шумний") — `git pull`

Ви просто виконуєте `git pull`. Git автоматично завантажить зміни колеги ("Звіти") і спробує "злити" (merge) їх з вашими ("Контакти").

  * **Якщо пощастить:** Зміни були в різних частинах файлу. Git сам їх об'єднає і створить новий "коміт злиття". Після цього ви зможете зробити `git push`.
  * **Якщо ні:** Ви отримаєте **конфлікт**.

### Шлях 2: Найкращий (чиста історія) — `git pull --rebase`

Це команда, яку я рекомендую. Вона робить те саме, але значно "охайніше".

  * **Що робить `rebase` (аналогія):**
    1.  Git "відкладає" ваш коміт ("Додав контакти") у тимчасову кишеню.
    2.  Завантажує зміни колеги ("Звіти"). Тепер ваш код виглядає точнісінько як на сервері.
    3.  Дістає ваш коміт з кишені і "накладає" його **зверху** змін колеги.

Ваша історія комітів виглядає чистою і лінійною, ніби ви робили свою роботу *після* колеги.

### Що робити при конфлікті?

Якщо і ви, і колега змінили *той самий рядок* (наприклад, заголовок `<h1>`), `rebase` (або `merge`) зупиниться.

1.  Git покаже вам файл з маркерами:
    ```html
    <<<<<<< HEAD
    <h1>Наші Контакти</h1>  =======
    <h1>Наші Звіти</h1>   >>>>>>> [хеш коміту]
    ```
2.  Ваше завдання — вручну відредагувати цей файл і вирішити, як він має виглядати. Наприклад, залишити обидва:
    ```html
    <h1>Наші Звіти</h1>
    <h1>Наші Контакти</h1>
    ```
3.  Після того, як ви прибрали всі `<<<`, `===`, `>>>` і зберегли файл:
      * Виконуєте `git add .` (щоб сказати Git, що ви вирішили конфлікт).
      * Виконуєте `git rebase --continue` (щоб продовжити процес).
4.  Тепер робите `git push`.

## Крок 5: Найкращі практики (Куди рухатись далі)

Попередні кроки охоплюють базу, але для справжньої командної роботи бракує *найголовнішого* — **гілок (branches)**.

  * **Проблема:** Працювати в `main` (або `master`) — небезпечно. Це як редагувати оригінал документа, а не копію.
  * **Що таке гілка?** Це "паралельна копія" вашого проєкту, де ви можете безпечно експериментувати, не ламаючи основний код.
  * **Новий "Професійний воркфлоу":**
    1.  `git pull` (Оновити `main`).
    2.  `git checkout -b feature/add-contacts` (Створити *нову гілку* для вашої задачі).
    3.  (Працюємо...) -> `add` -> `commit` (Комітимо у *свою* гілку).
    4.  `git push --set-upstream origin feature/add-contacts` (Пушимо *свою* гілку на GitHub).
  * **Pull Request:** Після цього ви створюєте на GitHub **Pull Request** (Запит на злиття). Це прохання: "Команда, я закінчив. Подивіться мій код у гілці `feature/add-contacts`. Якщо все добре, додайте його до `main`".

Це **найбезпечніший** спосіб командної роботи. Він захищає `main` від випадкових помилок.

## Контрольні питання

1.  **Проблема:** Ваш друг каже: "Я спробував зробити `git push`, але отримав помилку `[rejected]`. Що це означає і що сталося?"
2.  **Workflow:** Яка перша команда, яку ви маєте виконати, сівши за роботу над спільним проєктом, і чому?
3.  **Помилка:** Ваш колега каже: "Я склонував репозиторій, але він з'явився всередині іншого мого проєкту, і тепер нічого не працює". Що він зробив не так?
4.  **Конфлікт:** Поясніть своїми словами, чому `git pull --rebase` часто вважається кращим, ніж простий `git pull`.
5.  **Найкраща практика:** Чому (майже) ніколи не варто робити коміти напряму в гілку `main`?

<details markdown="1">
<summary>Відповіді (спробуйте спочатку відповісти самі)</summary>

1.  **Проблема:** Помилка `[rejected]` означає, що віддалений репозиторій (GitHub) **містить зміни (коміти), яких у вас немає локально**. Це сталося тому, що ваш колега зробив `git push` *раніше* за вас. Git не дозволяє вам "перезаписати" його роботу, тому відхиляє ваш `push` і просить вас спочатку завантажити зміни колеги (`git pull`).

2.  **Workflow:** Перша команда — **`git pull`** (або `git pull --rebase`). **Чому:** Щоб завантажити всі найсвіжіші зміни від колег і переконатися, що ви починаєте роботу з найактуальнішої версії коду. Це запобігає конфліктам у майбутньому.

3.  **Помилка:** Він виконав `git clone` всередині теки, яка вже була Git-репозиторієм. Це створило "Git-матрьошку" (`.git` всередині `.git`), і Git тепер не розуміє, з яким репозиторієм працювати.

4.  **Конфлікт:** `git pull` створює "коміт злиття" (merge commit), який "засмічує" історію проєкту і робить її схожою на складну діаграму. `git pull --rebase` **переписує історію**: він бере ваші коміти, "відкладає" їх, оновлює гілку до стану як на сервері, а потім "накладає" ваші коміти зверху. Історія залишається чистою, пласкою та лінійною, ніби ви працювали послідовно, а не паралельно.

5.  **Найкраща практика:** Гілка `main` вважається "золотою" або "виробничою" версією коду. Вона *завжди* має бути стабільною і робочою. Прямі коміти в `main` (особливо без тестів) можуть "зламати" проєкт для всієї команди. Робота в окремих **гілках** з подальшим **Pull Request** дозволяє команді перевірити (зробити код-рев'ю) ваші зміни *перед* тим, як вони потраплять у `main`.

</details>
