## "Людський фокус": Волонтерський хаос

Уявіть, що ми створили сайт для волонтерського логістичного центру. У години пік на сайт одночасно надходить 1000 запитів на секунду (наприклад, "потрібна допомога" або "хочу задонатити").

**Підхід 1: "Наївний" (`new Thread()`)**
На кожен запит ми наймаємо нового волонтера (створюємо `new Thread()`).

  * **Результат:** За 5 секунд у нас 5000 волонтерів. Вони миттєво вичерпують усі ресурси центру (місця, комп'ютери, каву). Менеджери не встигають їх координувати. Настає повний хаос, і система "лягає".

**Підхід 2: "Професійний" (Thread Pool)**
У нас є "зміна" з 10 досвідчених волонтерів, які працюють нон-стоп (це наш **пул потоків**).

  * **Результат:** Усі 1000 запитів на секунду потрапляють у **чергу (Queue)**. 10 волонтерів швидко розгрібають цю чергу один за одним. Робота йде стабільно, контрольовано, без хаосу.

## Проблема: Чому `new Thread()` — це шлях до катастрофи

Давайте подивимось на "наївний" підхід у коді.

**1. Створення потоку — це дорого.**
Кожен `new Thread()` — це звернення до Операційної Системи з проханням "виділи мені ресурси, стек, пам'ять...". Це займає час і ресурси.

**2. Ви не можете їх контролювати.**
Якщо 5000 користувачів одночасно натиснуть кнопку, ваша програма слухняно спробує створити 5000 потоків. Більшість систем просто "помруть" від такого навантаження, отримавши `OutOfMemoryError`. Ви ніяк не обмежуєте кількість "робітників".

**3. Ви не перевикористовуєте потоки.**
Потік виконав завдання (обробив запит за 100 мілісекунд) і "помер". На наступний ідентичний запит ви створюєте *новий* потік. Це все одно, що кожного разу для поїздки на таксі будувати новий автомобіль.

Ось як виглядає цей хаос:

```java
// ServerSimulator_Bad.java
public class ServerSimulator_Bad {

    public static void main(String[] args) {
        System.out.println("Запускаємо 'наївний' сервер...");
        
        // Імітуємо 1000 одночасних запитів
        for (int i = 0; i < 1000; i++) {
            // На КОЖЕН запит створюємо НОВИЙ потік
            Thread taskThread = new Thread(() -> {
                // Імітуємо роботу (напр., запит до бази даних)
                try {
                    Thread.sleep(1000); 
                } catch (InterruptedException e) {}
                // System.out.println("Запит оброблено потоком: " + Thread.currentThread().getName());
            });
            taskThread.start();
        }
        
        System.out.println("Сервер 'обробив' 1000 запитів...");
        // Насправді, ми просто запустили 1000 потоків, які борються за CPU
        // і можуть "вбити" нашу систему.
    }
}
```

## Рішення: `ExecutorService` — ваша команда "волонтерів"

Замість того, щоб керувати потоками вручну, ми **делегуємо** це завдання спеціальному сервісу — `ExecutorService`.

Ми просто кажемо: "Ось тобі 10 потоків-робітників (наш пул), а ось тобі черга завдань (`Runnable`). Далі роби сам".

### Як це виглядає на практиці

1.  **Створюємо пул:**
    Ми використовуємо фабричний клас `Executors`. Найпростіший варіант — `newFixedThreadPool`.

    ```java
    // Створюємо "зміну" з 10 волонтерів (потоків)
    int corePoolSize = 10;
    ExecutorService executor = Executors.newFixedThreadPool(corePoolSize);
    ```

2.  **Віддаємо завдання:**
    Замість `new Thread().start()` ми використовуємо `executor.submit(task)`.

    ```java
    // Наша задача (та сама, що й раніше)
    Runnable task = () -> {
        try {
            Thread.sleep(1000); 
        } catch (InterruptedException e) {}
    };

    // Відправляємо завдання в чергу
    executor.submit(task);
    ```

3.  **Закриваємо пул (Важливо\!):**
    Коли всі завдання роздані, ми маємо "закрити" пул, інакше програма ніколи не завершиться.

      * `executor.shutdown();` — м'яка зупинка. Пул перестане приймати нові завдання, але виконає ті, що вже є в черзі.

### Фінальний код (Правильний підхід)

```java
// ServerSimulator_Good.java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ServerSimulator_Good {

    public static void main(String[] args) {
        System.out.println("Запускаємо 'професійний' сервер...");
        
        // 1. Створюємо пул з 10 потоків. Більше 10 потоків ОДНОЧАСНО не буде.
        ExecutorService executor = Executors.newFixedThreadPool(10);

        // Імітуємо 1000 одночасних запитів
        for (int i = 0; i < 1000; i++) {
            
            Runnable task = () -> {
                // Імітуємо роботу
                try {
                    Thread.sleep(1000);
                } catch (InterruptedException e) {}
                // System.out.println("Запит оброблено потоком: " + Thread.currentThread().getName());
            };
            
            // 2. Віддаємо завдання в чергу. 
            // Executor сам візьме його, коли один з 10 потоків звільниться.
            executor.submit(task);
        }
        
        // 3. Кажемо пулу, що нових завдань не буде.
        executor.shutdown();
        
        System.out.println("Сервер прийняв 1000 запитів на обробку...");
        // Програма завершиться сама, коли останній з 10 потоків
        // виконає останнє завдання з черги.
    }
}
```

## Що, як завданню потрібно повернути результат? (`Callable` та `Future`)

Досі наші "волонтери" просто виконували роботу і нічого не повертали (`Runnable` має метод `void run()`). Але що, як нам потрібно, щоб потік виконав складне обчислення і **повернув нам результат**?

Наприклад, наш волонтерський центр хоче порахувати загальну потребу в медикаментах, опитавши 10 різних складів одночасно. Кожне опитування — це окреме завдання, яке має повернути число.

Для цього існує пара `Callable` та `Future`.

1.  **`Callable<V>`:** Це як `Runnable`, але з двома відмінностями:

      * Його метод `call()` **повертає значення** (типу `V`, наприклад `Callable<Integer>`).
      * Він **може кидати виняток** (`throws Exception`), що значно спрощує обробку помилок.

2.  **`Future<V>`:** Це "обіцянка" або "контейнер" для результату, який *ще не готовий*. Коли ви відправляєте `Callable` в `ExecutorService`, він негайно повертає вам `Future`. Ви можете тримати цей об'єкт у себе, а результат з нього отримати пізніше.

### Як це виглядає на практиці

Давайте симулюємо наш логістичний центр, який паралельно опитує 3 склади.

<details markdown="1">
<summary>Натисніть, щоб побачити повний код прикладу</summary>

```java
// AidCalculator.java (Наше завдання, що повертає результат)
import java.util.concurrent.Callable;
import java.util.concurrent.ThreadLocalRandom;

// Callable<Integer> означає, що цей потік поверне ціле число
public class AidCalculator implements Callable<Integer> {
    
    private String warehouseName;

    public AidCalculator(String warehouseName) {
        this.warehouseName = warehouseName;
    }

    @Override
    public Integer call() throws Exception {
        // Імітуємо складну роботу (наприклад, запит до БД складу)
        System.out.println("🧮 " + warehouseName + ": починаю підрахунок...");
        int processingTime = ThreadLocalRandom.current().nextInt(1000, 5000);
        Thread.sleep(processingTime);
        
        // Імітуємо результат
        int itemsNeeded = ThreadLocalRandom.current().nextInt(100, 1000);
        System.out.println("✅ " + warehouseName + ": потрібно " + itemsNeeded + " од.");
        
        // Повертаємо результат
        return itemsNeeded;
    }
}
```

А тепер головний клас, який запускає ці завдання і **збирає результати**:

```java
// LogisticsCenter.java (Головний клас)
import java.util.concurrent.*;

public class LogisticsCenter {

    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(3);
        System.out.println("🚀 Центр починає паралельне опитування складів...");

        // 1. Створюємо завдання
        Callable<Integer> task1 = new AidCalculator("Склад (Київ)");
        Callable<Integer> task2 = new AidCalculator("Склад (Львів)");
        Callable<Integer> task3 = new AidCalculator("Склад (Харків)");

        // 2. Відправляємо завдання і ОТРИМУЄМО "ОБІЦЯНКИ" (Future)
        Future<Integer> future1 = executor.submit(task1);
        Future<Integer> future2 = executor.submit(task2);
        Future<Integer> future3 = executor.submit(task3);

        // 3. Отримуємо результати (тут починається магія)
        // 
        // future.get() - це БЛОКУЮЧА операція.
        // Головний потік (main) "зависне" на цьому рядку,
        // доки 'task1' не завершить роботу і не поверне результат.
        int totalNeeded = 0;
        
        System.out.println("⏳ Головний потік чекає на результат з Києва...");
        totalNeeded += future1.get(); // <-- Блокуємо і чекаємо
        
        System.out.println("⏳ Головний потік чекає на результат зі Львова...");
        totalNeeded += future2.get(); // <-- Блокуємо і чекаємо
        
        System.out.println("⏳ Головний потік чекає на результат з Харкова...");
        totalNeeded += future3.get(); // <-- Блокуємо і чекаємо

        // 4. Виводимо фінальний результат
        System.out.println("==========================================");
        System.out.println("📈 ЗАГАЛЬНА ПОТРЕБА: " + totalNeeded + " од.");
        System.out.println("==========================================");

        executor.shutdown();
    }
}
```
</details>

### Погляд у майбутнє: `CompletableFuture`

Як ви помітили, `future.get()` **блокує** наш головний потік. Це вже краще, ніж нічого, але не ідеально.

Сучасна Java (8+) пропонує значно потужніший інструмент — **`CompletableFuture`**.

Це еволюція `Future`, яка дозволяє будувати **ланцюжки асинхронних операцій** у неблокуючому стилі. Замість того, щоб питати "результат готовий?" і чекати (`get()`), ви кажете: "Ось, візьми це завдання, а **КОЛИ** воно буде виконано, **ТОДІ** візьми його результат і зроби з ним *ось це*".

```java
// Приклад філософії CompletableFuture (це не робочий код, а ілюстрація)

// НЕ ТАК (блокуючий стиль):
// Future<String> future = executor.submit(...);
// String result = future.get(); // <- ЧЕКАЄМО
// System.out.println(result);

// А ТАК (неблокуючий стиль):
CompletableFuture.supplyAsync(() -> {
    // ... тут виконується складне завдання ...
    return "Ось результат";
})
.thenApply(result -> {
    // ... цей блок виконається, КОЛИ результат буде готовий ...
    return result.toUpperCase();
})
.thenAccept(finalResult -> {
    // ... а цей блок виконається ПІСЛЯ попереднього ...
    System.out.println(finalResult); // Надрукує "ОСЬ РЕЗУЛЬТАТ"
});

// Головний потік при цьому не блокується і може робити іншу роботу
```

Це надзвичайно потужна концепція, яка є основою сучасної асинхронної розробки в Java.

## Що далі? (Інші типи пулів)

Ми використали `newFixedThreadPool` (фіксована кількість потоків). Але існують й інші:

  * **`newCachedThreadPool`:** "Еластичний" пул. Створює нові потоки за потребою і "вбиває" ті, що простоюють. Добре для великої кількості коротких завдань.
  * **`newSingleThreadExecutor`:** Пул з одного потоку. Гарантує, що всі завдання будуть виконані послідовно, одне за одним, в однму потоці.

## ✅ Контрольні питання

1.  **Проблема:** Назвіть три головні причини, чому `new Thread()` для кожного запиту на сервері — це погана ідея.
2.  **Аналогія:** Поясніть своїми словами, як "пул потоків" вирішує цю проблему, використовуючи аналогію з кухнею ресторану або кол-центром.
3.  **Рішення:** Як називається клас, який ми використовували для керування пулом потоків? Яку команду ми використали, щоб створити пул з 5 потоків?
4.  **Застосування:** Яка різниця між `thread.start()` та `executor.submit(task)`?
5.  **Життєвий цикл:** Що робить команда `executor.shutdown()` і чому вона є обов'язковою?
6.  **Повернення результатів:** У чому ключова різниця між `Runnable` та `Callable`?
7.  **Future:** Яку проблему вирішує `Future` і який його головний недолік (пов'язаний з методом `get()`)?

<details markdown="1">
<summary>Відповіді (спробуйте спочатку відповісти самі)</summary>

1.  **Три причини:**

    1.  **Дорого:** Створення системного потоку — це "важка" операція для ОС.
    2.  **Неконтрольовано:** Можна легко створити тисячі потоків і "вбити" систему (отримати `OutOfMemoryError`).
    3.  **Неефективно:** Потоки не перевикористовуються; вони створюються і вмирають для кожного завдання.

2.  **Аналогія (кухня):**

      * **`new Thread()`:** Це як наймати нового кухаря на кожне окреме замовлення (навіть на одну каву). Кухня миттєво переповниться, почнеться хаос, і ніхто не зможе працювати.
      * **Пул потоків:** Це як мати постійну зміну з 5 кухарів. Всі замовлення потрапляють у чергу. Як тільки кухар звільнився, він бере наступне замовлення. Це контрольовано, ефективно, і кухарі (потоки) не простоюють.

3.  **Клас та команда:**

      * **Клас:** `ExecutorService`
      * **Команда:** `Executors.newFixedThreadPool(5)`

4.  **Різниця:**

      * `thread.start()`: Це пряма команда для JVM "створи новий потік і запусти його".
      * `executor.submit(task)`: Це команда для `ExecutorService` "візьми це завдання (`task`) і постав його в чергу. Коли один з твоїх потоків-робітників звільниться, нехай він його виконає". Ми делегуємо керування.

5.  **`executor.shutdown()`:** Ця команда каже пулу потоків: "Більше нових завдань не приймати, але завершити ті, що вже є в черзі". Вона **обов'язкова**, тому що потоки в пулі зазвичай "живі" і чекають на нову роботу. Без `shutdown()` програма (і JVM) ніколи не завершить своє виконання.

6.  **`Runnable` vs `Callable`:**

      * `Runnable`: Його метод `run()` має тип `void` (нічого не повертає) і не може кидати перевірювані винятки.
      * `Callable`: Його метод `call()` повертає значення (напр., `Integer`) і може кидати винятки (`throws Exception`).

7.  **`Future`:**

      * **Проблема, яку вирішує:** Дозволяє отримати результат (`Integer`, `String` тощо) з асинхронного завдання, виконаного в іншому потоці.
      * **Головний недолік:** Метод `future.get()` є **блокуючим**. Це означає, що головний потік "зависне" і буде чекати, доки завдання не завершиться. Це зупиняє роботу і є неефективним (цю проблему вирішує `CompletableFuture`).

</details>
